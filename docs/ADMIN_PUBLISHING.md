# 课程与学习资料发布

本功能已在独立分支完成，本说明不代表已部署。上线后进入 `/admin`，完成原有管理员二次验证，再打开“课程与资料”。账号管理仍在“用户”。

## 每次更新

1. 选择“课程与教学班”或“学习资料”。下载空白模板，新增时填写；修改已有内容时先“导出当前目录”，保留原编号。
2. 上传 UTF-8 CSV 或 XLSX；XLSX 有多个工作表时选择实际数据表，禁止公式。资料也可直接在后台填写标题、分类、说明和课程关联，再选择上传文件或填写 HTTPS 链接。
3. 点击“校验并预览”。逐项修正行号对应的错误，核对新增、修改、删除及提示。没有出现在本批表格里的旧记录会保留。
4. 填写至少 8 字的发布说明，确认必要提示，点击“确认发布到网站”。发布成功后，新访问会读取新的目录；已打开页面保留其固定版本，刷新可读取更新。

预览有效期为 20 分钟，每位管理员最多保留 3 份未发布预览，可直接丢弃。二次验证过期须重新验证；他人已更新目录时须重新校验，旧预览不能覆盖新版本。上传表格的文件限制为 8 MiB、10,000 行；实际提交和完整目录还受服务端预算约束，超限会明确拒绝。

## 课程表格

课程号、教学班编号和时段编号分别标识目录课程、实际教学班及上课时段。同名课程不能合并，教师、主修班级、课序号属于教学班；周次、星期、节次、地点属于时段。每个时段填写一行，同一教学班有几个时段就填写几行。无时段的目录课程可单独填写课程信息。

优先从当前目录导出后修改，课程号等编号在 Excel 中设为文本，防止丢失前导零。新增教学班和时段使用明确、稳定且不重复的编号。专业关系须填写实际专业编号和年级，不通过名称猜测。当前沿用网站已有的 `fall/spring` 学期与大一至大四模型，周次支持 1–18 周的精确集合，包括半学期、单双周和不连续周。

“新增或更新”只调整明确提供的记录；删除时段须显式填写“删除时段”。变更教师、主修班级或课序号会要求核对教师身份提示，系统不会按同名教师自动关联评价。教室、周次等调整只在身份可证明不变时继承既有教师来源；原来源撤回仍会使映射失效。此处更新公共目录，不修改学生的官方教务导入或个人课表。

## 学习资料

资料可以关联一门或多门现有课程，按课程号选择，不按同名课程合并。新增资料的编号由后台生成；编辑、下架与批量更新须保留原资料编号，已有收藏按该编号继续解析。

- 文件上传支持 PDF、PPTX、DOCX、XLSX、ZIP，单文件最多 25 MiB；上传成功仍是私有待发布文件，只有关联资料成功发布后才能公开下载。文件内容与 ZIP 边界会校验；宏、异常路径和超限压缩包会拒绝。
- 外部资料使用 HTTPS 链接。本站不代抓外链文件，未知大小显示“大小未标注”；可用于网盘及较大文件，访问权限仍由外部服务管理。
- 修改标题、分类、说明和课程关联可直接加入本批；批量资料表格与直接填写的内容使用同一校验及发布流程。
- 下架只移除当前目录入口。已公开的不可变链接及浏览器缓存不承诺立即失效；文件若必须彻底移除，须另行维护文件和缓存，不能把目录下架当作撤销下载权限。

历史资料基线含 457 条记录、439 个唯一资料编号。导出会合并同编号的课程关联；没有修改的原记录保留。显式修改重复编号时会提示其多条历史记录将合并，不悄悄覆盖。

## 恢复与容量

“发布记录与恢复版本”可以恢复先前已发布版本或初始目录，须填写说明。恢复也会生成新的发布记录与递增版本序号；课程恢复若会破坏当前资料的课程关联，会拒绝并要求先调整资料。发布和审计在同一数据库事务内提交，失败不留下半批目录。恢复资料目录不会自动撤回已公开文件。

发布采用一次生成、固定版本读取：完整课程和轻量首页投影共享目录身份，gzip、ETag 和长期缓存减少重复传输；首页继续按需加载完整课表。当前版本指针采用短缓存，公开读取不创建匿名账号或写访问限流表。单进程保留至多 3 份、合计 12 MiB 的快照缓存，并限制同时解码的数量；导入与上传有串行保护。

服务端完整课程 JSON 最多 3,250,000 字节、轻量课程 750,000 字节、资料目录 420,000 字节，草稿请求最多 4 MiB。当前完整课程基线已接近预算，大批增加课程若超限，应先在隔离容器测量再调整预算，不能直接取消限制。发布快照最多 200 份、压缩内容合计 100 MiB；达到上限会拒绝继续发布，不自动清除恢复记录。

新上传资料使用独立持久卷，总量最多 1 GiB（含待发布和已发布文件），待发布文件另限 250 MiB、全站 50 份、每管理员 5 份，24 小时过期后在后续操作中清理。大文件及持续增长的资料库应迁移到对象存储，避免占满现有系统盘；已在外部存储的旧资料不复制到新卷。

认证容器配置从 128 MiB 调整至 256 MiB，Node 老生代 64 MiB、半生代 4 MiB。本机 Windows Node 24 + PostgreSQL 17 的真实 store 全流程测量包含 5,881 行表格、发布、读取、回退，以及两路并发 Argon2，峰值约 201 MiB；全表预览约 527 ms、发布约 284 ms，最大事件循环停顿约 397 ms。192 MiB 不足，因此候选配置增加余量。正式部署前仍须在实际 Linux 容器验证全量表格、并发访问和登录；本机测量不能代替生产容量结论。可复现脚本为 `services/auth-api/scripts/catalog-native-store-load-check.mjs`，仅接受其专用本机合成 PostgreSQL 测试服务，不连接生产。

## 部署与维护

需要同步更新 app、auth-api、0029 数据库迁移、对应环境的网关和 Compose。新配置包括 `AUTH_CATALOG_UPLOAD_DIR=/srv/catalog-files` 与独立资料卷；app 的 `CATALOG_API_ORIGIN` 必须指向本环境明确配置的 HTTPS 域名。生产与 staging 的新资料卷、数据库及上游代理分别独立，不能覆盖现场额外的图书馆与网络配置。

`/api/catalog/*` 与 `/resources/files/uploads/*` 由本网关转发到本环境 auth-api。旧静态资料路径保留。未配置目录时后台明确禁用文件上传，链接资料仍可操作；已配置公共目录 API 故障时不悄悄回退到旧目录。

数据库备份与恢复还须同步备份新增资料卷；仅恢复 PostgreSQL 不会恢复上传文件。回滚旧应用前应保存发布指针、版本与新卷，避免旧应用忽略新目录而造成“恢复成功”的误判。

原始静态课程或资料文件改变后执行 `npm run build:catalog-baseline`，再运行 `node --test tests/catalog-delivery.test.mjs`，使 auth 镜像的 gzip 初始目录与主站源文件一致。新公开版本由数据库发布，不依赖每次重新构建网站。
